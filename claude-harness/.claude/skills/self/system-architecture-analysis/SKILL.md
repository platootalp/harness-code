# 系统架构分析

## 概述

使用 C4 模型将代码库中某个系统、模块或机制的结构梳理清楚，生成一篇**自包含、可顺序阅读**的架构解析文档。

**核心方法：** 采用 C4 模型逐层深入：Context（系统边界）→ Container（模块拆分）→ Component（模块内部）。从整体到部分地展示系统的架构设计。

**与 deep-functional-analysis 的区别：**
- 本技能：C4 模型 + 架构分层，聚焦系统结构
- deep-functional-analysis：问题驱动 + 逐步深入，聚焦单一功能/机制

## 何时使用

- 用户要求分析某个系统/模块/机制的结构
- 用户说"分析 X 系统的架构"、"梳理 Y 模块的结构"、"解析 Z 组件的设计"
- 用户需要理解某个子系统的模块划分、组件关系、边界定义
- 即使用户只说"看看这个模块的结构"，也应使用此技能生成结构化架构文档

**不适用：** 深入分析某个功能/机制的原理 → 使用 `deep-functional-analysis`

## 核心原则

### C4 模型原则

- **第三章使用 C4 Context + Container + 工作流概览图**：展示系统边界与外部交互、模块拆分与职责、与周边模块的交互序列
- **第五章每个模块使用 C4 Component + 模块内部流程图**：展示模块内部组件、模块内部时序图
- **每张 C4 图后必须有内容解释**：解释图中关系、数据流向、设计决策，而非读图指引

### 从整体到部分原则

- **第三~四章全局视角**：不深入模块实现
- **第五章才进入模块内部**：每个模块单独解析
- **禁止先写模块再写整体**：必须整体在前、模块在后

### 内容优先原则

- **正文以连贯叙述为主体**：禁止路径列表拼凑
- **先回答核心问题**：是什么、为什么、如何运行、如何失败
- **证据后置**：证据索引统一放到第七章

### 图示原则

- **每篇文档至少 6 张 Mermaid 图**：C4 图、时序图、状态图等
- **每张图后必须有解释**：格式为关系层、流向层、决策层、影响层
- **节点着色规范**：蓝色核心组件、绿色成功/完成、橙色中间/警告、红色失败/错误、紫色跨系统交互

## 工作流程

### Step 1：探索与定位

```
1.1 确认参数（分析目标、输出路径、语言）
1.2 定位核心文件（Glob 搜索文件名、Grep 搜索关键词/类名/函数名）
1.3 识别系统边界（入口函数/类、外部依赖、上下游系统）
```

**产出：** 核心文件清单 + 系统边界描述

### Step 2：深挖与建模

```
2.1 追踪调用链（逐跳：调用方→被调用方、输入、输出、副作用、失败模式；至少 2-3 条高价值链路）
2.2 追踪数据流（入口→存储/输出完整路径，每步格式转换，存储位置）
2.3 识别状态流转（核心实体状态枚举/联合类型、流转条件、终态、异常状态）
2.4 识别模块划分（职责内聚性拆分 3-7 个模块，模块间通信方式）
2.5 收集设计取舍（设计决策点、替代方案、取舍代价；至少 4 组可量化）
```

**产出：** 调用链清单 + 数据流路径 + 状态机 + 模块划分 + 设计取舍

### Step 3：生成文档

```
3.1 第一、二章：目录 + 概述表 + 核心概念定义
3.2 第三章（架构总览）：C4 Context 图 + C4 Container 图 + 工作流概览图 + 各模块职责概述表
3.3 第四章（核心工作流）：核心工作流程时序图（正常流 + 异常流）+ 核心实体状态流转图
3.4 第五章（分模块详解）：每个模块：C4 Component 图 + 数据结构代码块 + 存储与持久化 + 模块内部时序图 + 与其他模块的交互
3.5 第六、七章：设计取舍对比表 + 总结 + 文件索引
```

**产出：** 完整文档初稿

### Step 4：验证与修复

```
4.1 完整性：7 章覆盖、正常流+异常流、设计取舍≥4组、Mermaid图≥6张
4.2 一致性：术语一致、图与正文一致、代码与源码一致
4.3 深度：逐跳调用链、连续叙述（非列表拼凑）、量化取舍、边界条件
4.4 修复问题，输出终稿
```

**产出：** 最终文档

## 输出结构

每篇文档遵循 7 章结构，采用 C4 模型逐层深入：

```
一、概述              — 系统定位、关系总览
二、核心概念          — 术语体系、类型签名
三、架构总览          — C4 Context + Container + 工作流概览 + 各模块职责
四、核心工作流        — 核心工作流程 + 核心实体状态流转
五、分模块详解        — C4 Component + 模块内部结构化解析
六、设计原理与对比分析 — 设计取舍 + 对比 + 原则
七、总结与索引        — 关系表 + 原则 + 洞察 + 文件索引
```

**章节增减规则：** 不适用章节在目录标注 `*(不适用)*`；可追加章节编号从八开始；已有章节顺序不可调换。

## 常见借口

| 借口 | 事实 |
|---|---|
| "这个系统很简单，不需要 C4 图" | 任何系统都需要边界定义；要求至少 6 张 Mermaid 图 |
| "没有模块划分" | 必须拆分为 3-7 个模块；职责内聚性分析是架构分析核心 |
| "代码就是证据" | 代码路径不能替代解释；必须先解释原理再引用代码 |
| "异常流不重要" | 核心工作流必须包含正常流 + 至少 1 条异常流 |
| "设计取舍很难量化" | 至少给出具体说明；禁止"大概"、"应该"等模糊表述 |
| "从模块讲起更直接" | 必须从整体到部分；先 Context/Container，再 Component |

## 危险信号

- 缺少 C4 Context 图或 C4 Container 图
- C4 图后只有"这张图展示了..."的读图指引，没有内容解释
- 章节顺序错误：先写模块再写整体
- 主文以路径列表、文件列表、占位条目为主，无连续叙述
- 调用链只写步骤，不写输入/输出/失败模式
- 没有设计取舍章节，或设计取舍没有量化
- 缺少异常流章节
- 缺少数据结构代码块
- 节点着色不规范
- 缺少文件索引

## 示例

**差：** 先按章节复述结构，最后说"整体架构清晰"。

**好：** 直接展示 C4 图，然后解释："系统采用注册-装配-执行三层架构：注册层收集所有可用工具定义（内置 + MCP 动态源），装配层按权限规则和模式过滤后合并为工具池，执行层对工具调用做并发/串行分区后逐个执行。"

**差：** "相关文件：src/tools/permissions.ts, src/tools/canUseTool.ts。权限检查流程：deny → ask → checkPermissions → auto → safety。"

**好：** "权限检查采用多步管道：先检查 deny 规则，再检查 ask 规则，然后调用工具级 checkPermissions。经过 auto mode AI 分类器和内容级规则后，最后做安全检查。管道设计使得任何一步返回 deny 即短路退出，避免后续不必要的计算。"

**差：** "采用冻结快照而不是实时更新。"

**好：** "当前方案：冻结快照。替代方案：实时更新。为何不选：实时更新下每次写入后首次 API 调用成本翻倍。代价量化：冻结快照缓存命中可节省 30-50% 的输入 token 费用（取决于快照大小）。"
