# 项目简历模板

## 填充指南

- `[ ]` 标记为必填项
- `[待补充]` 表示代码中无数据，需用户提供真实数据后再替换
- 每条信息后可附 `(来源: xxx)` 标注数据出处，正式版中删除来源标注

---

## 模板

### 项目背景

[ ] 一段话说清：项目目标 + 核心能力 + 在技术体系中的定位

**示例格式：**

> 为 [目标]，构建 [项目定位]，支持 [核心能力列表]；在 [核心模块列表] 形成一体化能力，作为 [技术体系定位]，支撑 [业务流程闭环]。

**关键要素：**
- 项目要解决什么问题
- 项目的核心能力边界（能做什么）
- 项目在更大技术体系中的角色

---

### 技术栈

[ ] 用 `+` 连接的一行式展示，按技术层次从底层到上层排列

**格式：**

> Python + Pydantic + LiteLLM + FastMCP + SQLite + Milvus + Phoenix + Typer + Rich

**示例：**

> TypeScript + React + Next.js + Tailwind + Prisma + PostgreSQL + Redis + Docker

**提取方式：**
- 从 `pyproject.toml` / `package.json` / `Cargo.toml` / `go.mod` 提取核心依赖
- 从 `import` 语句验证实际使用情况（仅列出真正在核心模块中使用的）
- 排列顺序：语言 → 框架 → 核心库 → 存储 → 基础设施 → 工具链
- 不列次要/工具性依赖（如 linter、formatter），聚焦核心架构依赖
- 用 `+` 连接，一行写完，紧凑有力

---

### 核心工作

[ ] 4-6 个维度，每个维度 3-5 个要点

**每个维度的结构：**

> **维度名称**：
> - 要点1（一个独立的功能实现点，高层技术说明，不写代码级细节）
> - 要点2
> - 要点3
> - 要点4（如有）

**完整示例：**

> **多智能体编排与自适应路由**：
> - 构建 Orchestrator-Worker 状态中枢，集成 ReAct 循环与全局上下文管理，引入意图识别与智能澄清机制
> - 协同 5 类领域专家 Agent 分工执行，按职责隔离任务边界
> - 设计复杂度-风险双维路由算法，动态匹配 QUICK/DEEP/STRATEGIC 三种执行模式
> - 支持简单任务快速响应与复杂任务并行调度

**每个要点的写法原则：**
- 每个要点是一个独立的功能实现点，描述做了什么和怎么设计的
- 高层技术说明，禁止出现文件路径、环境变量名、函数名、配置字段名等代码级细节
- 自然地在描述实现时体现设计意图，而不是分开讲"为什么"和"怎么做"
- 有可量化事实就自然嵌入，没有就不强加

**维度提炼方法：**
1. 从代码目录结构识别模块边界
2. 从核心类/接口识别设计模式
3. 从调用链识别模块间协作关系
4. 从配置/常量识别可量化事实

**维度命名规范：**
- 使用"技术手段 + 核心价值"的命名方式
- 例：`分层上下文架构与动态压缩`、`统一 Tool 架构与安全编辑`
- 避免：`上下文模块`（太笼统）、`优化了上下文管理`（太模糊）

**可量化事实的类型（不杜撰指标时可用）：**
- 集成的工具/插件/模块数量
- 支持的类型/模式/策略数量
- 抽象层级数（如"三层架构"、"四级容错"）
- 支持的功能列表（如"文件操作/LSP/Web 检索/任务管理"）
- 设计模式数量（如"5 类领域专家 Agent"）

**涉及指标时的处理：**
- 代码/文档中有明确数据 → 直接引用，标注来源
- 代码中有基准测试但无结论 → 描述基准测试的存在，不编造结论
- 完全没有数据 → 用 `[待补充]` 标注，或用可量化事实替代

---

### 项目成果

[ ] 用真实数据展示项目效果

**格式：**

> [指标名] [数值] | [指标名] [数值]

**示例：**

> 需求 AI 渗透率 89.1% | AI 代码采纳率 62.5%

**如果没有现成指标：**
- 写 `[待补充]`，提示用户补充真实数据
- 可以从代码中找到的替代事实：
  - 代码规模（XX 个核心模块，XX 行代码）
  - 功能覆盖（支持 XX 类工具/XX 种协议）
  - 项目活跃度（XX 次提交/XX 个贡献者）
- 绝不杜撰百分比指标

---

## 聚焦模式

当用户指定自己 owner 的模块时：

1. 仅探查指定模块的目录和依赖
2. 技术栈只列该模块直接使用的
3. 核心工作只写该模块的维度
4. 项目成果写该模块相关的（如无，标注 `[待补充]`）
5. 项目背景保留完整（需要理解整体），但标注用户的聚焦范围

---

## 输出规范

1. 语言：中文叙述 + 英文技术术语（如 ReAct、RAG、DAG、Orchestrator-Worker、Topological Sort、Semantic Search 等），不自行翻译或杜撰术语，不确定时先搜索确认业界标准用法
2. 篇幅：整个简历控制在 300-500 字（不含技术栈列表）
3. 重点：核心工作每个维度 50-80 字，信息密度优先
4. 格式：Markdown，适合直接粘贴到简历或文档
5. 语气：专业、克制、事实驱动，避免营销话术
