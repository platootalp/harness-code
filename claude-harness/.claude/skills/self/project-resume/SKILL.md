# 项目简历生成器

从代码库中提炼项目核心价值，生成事实驱动的结构化项目简历。核心理念：**一切以代码和文档中的事实为准，没有数据支撑的指标不得杜撰。**

## 何时使用

- 用户要求总结项目、提炼亮点、写项目简历
- 用户要求生成求职简历中的项目经历部分
- 用户需要年终总结或技术分享中的项目描述
- 用户指定自己 owner 的模块，要求只写该部分
- 用户需要从代码库反推技术架构和核心工作

## 系统边界

**在范围内：**
- 从代码结构、配置文件、文档、提交历史中提取事实
- 分析架构模式、技术选型、模块职责、设计决策
- 生成结构化的项目简历（项目背景 + 技术栈 + 核心工作 + 项目成果）
- 支持用户指定关注范围（某个模块/自己 owner 的部分）

**不在范围内：**
- 为不存在的指标编造数据（如性能提升百分比、bug 率降低等）
- 替代正式的架构文档或设计文档
- 生成营销材料或夸大性宣传文案
- 对竞品做对比评价

## 核心工作流

### 第一步：项目探查

使用 Explore agent 对代码库做系统性扫描，收集以下事实：

1. **项目定位**：README、package.json/pyproject.toml 中的描述、项目名、仓库名
2. **技术栈**：依赖文件（requirements.txt、package.json、Cargo.toml、go.mod 等）、import 语句、配置文件
3. **架构骨架**：目录结构、模块划分、入口文件、核心类/函数
4. **设计模式**：代码中实际使用的模式（Orchestrator-Worker、ReAct、DAG、事件驱动等）
5. **规模数据**：代码行数、文件数量、模块数量、工具/插件数量（可从代码中客观统计的）
6. **文档事实**：CHANGELOG、设计文档、API 文档中记载的指标或成果

### 第二步：核心亮点提炼

从探查结果中提炼核心工作维度。每个维度需要：

1. **有代码证据**：探查时深入到文件和类级别，但输出时只写高层技术说明
2. **有设计意图**：说明为什么这样设计、解决了什么问题
3. **有可量化事实**（如果有）：代码中可客观统计的数据（模块数、工具数、支持的类型数等）
4. **不杜撰指标**：如果代码/文档中没有性能数据，就不要写"提升 X%"之类的话
5. **高层抽象**：要点描述做了什么和怎么设计的，不写文件路径、环境变量名、函数名、配置字段名等代码级细节

### 第三步：结构化输出

按以下模板生成项目简历。每个部分都有明确要求，详见 `references/resume-template.md`。

### 第四步：用户校准

生成初稿后，主动询问用户：
- 是否要聚焦于自己 owner 的模块？（如果项目大，默认全部核心亮点；用户指定后只写该部分）
- 指标是否需要补充？（提醒用户：代码中没有的指标不会杜撰，用户可手动补充真实数据）
- 语气和详略程度是否合适？

## 约束条件

1. **事实驱动**：所有描述必须有代码或项目文档支撑。如果一个架构模式只在代码中隐含但未显式命名，可以从代码结构推断但需标注"从代码结构推断"
2. **指标不杜撰**：如果代码/文档中没有"性能提升 X%"的数据，绝不可编造。可以用可量化的事实替代，如"集成 15+ 内置工具"、"支持 5 类领域专家 Agent"
3. **可量化优先**：优先使用代码中可客观统计的数字（模块数、文件数、支持的功能数、配置项数等）
4. **技术术语用英文行业标准**：技术术语使用业界公认的英文术语（如 ReAct、RAG、DAG、Orchestrator-Worker、Topological Sort、Semantic Search 等），不自行翻译或杜撰术语；如果不确定某个术语是否为业界标准，先用网络搜索确认再使用
5. **高层技术说明**：每个核心工作维度用 3-5 个要点展开，每个要点是一个独立的功能实现点，描述**做了什么、怎么设计的**，而非代码怎么写的；禁止出现文件路径（如 `~/.openharness/teams/`）、环境变量名（如 `CLAUDE_CODE_COORDINATOR_MODE`）、函数名/类名（如 `_build_coordinator_context_message()`）、配置字段名（如 `max_turns`）等代码级细节；关键设计用粗体标注
6. **用户视角**：项目简历服务于求职/展示，需突出个人贡献和技术深度，但必须诚实
7. **范围可控**：项目内容过多时，用户可指定自己主要 owner 的部分，只生成该部分内容

## 验收标准

生成的项目简历应满足：

- [ ] 项目背景一段话说清项目定位和目标
- [ ] 技术栈用 `+` 连接的一行式展示，不遗漏重要技术
- [ ] 核心工作 4-6 个维度，每个维度 3-5 个要点
- [ ] 每个要点是高层技术说明，描述做了什么和怎么设计的，不含文件路径、环境变量、函数名等代码级细节
- [ ] 没有杜撰的性能指标或效果数据
- [ ] 项目成果使用代码/文档中的真实数据，或标注"待补充"
- [ ] 整体语言精炼专业，适合简历/年终总结场景

## 正反示例

### 正例：核心工作描述（分点格式，高层技术说明）

> **分层上下文架构与动态压缩**：
> - 构建常驻上下文 + JIT 本地探索 + RAG 远程检索三层上下文架构，按信息重要性评分分级处理
> - 实现 Token 阈值触发压缩，长上下文无损卸载（工具结果持久化本地文件，窗口仅保留引用路径），支持按需加载
> - 建立 Subagent 任务级隔离，执行摘要回传主会话，避免上下文交叉污染
> - 集成 RAG 远程检索，支持万行级代码库的精准语义召回

**为什么好**：4 个要点各是一个独立功能点，描述的是架构设计和实现策略（三层怎么组织的、压缩怎么做、隔离怎么设计），不涉及文件路径、函数名等代码级细节。

### 反例：过于细节，泄露代码实现

> ~~**Swarm 团队协作与跨进程消息系统**：
> - 实现持久化团队生命周期管理，以 `~/.openharness/teams/<name>/team.json` 存储团队元数据
> - 构建基于文件系统的异步 Mailbox 消息队列（`inbox/<timestamp>_<id>.json`），使用 exclusive file lock + 原子 rename 保证并发安全
> - 实现 `SwarmPermissionRequest/Response` 跨进程权限同步协议，通过 `poll_permission_response()` 轮询授权结果~~

**为什么不好**：混入了文件路径（`~/.openharness/teams/`、`inbox/`）、函数名（`poll_permission_response()`）、类名（`SwarmPermissionRequest/Response`），这些是代码级细节，简历读者不需要也不关心。应该提升到架构层面描述。

**改为**：
> - 实现持久化团队生命周期管理，支持跨会话团队恢复与成员状态追踪
> - 构建异步 Mailbox 消息队列，使用文件锁与原子写入保证并发安全
> - 实现跨进程权限同步协议，解决子进程 Agent 在无交互终端环境下的权限审批问题

### 反例：杜撰指标

> ~~代码编辑冲突率降低 85%~~

**为什么不好**：如果代码/文档中没有这个 85% 的数据来源，这就是杜撰的。应该替换为可量化事实，如"实现哈希锚定并发冲突检测（LINE#ID + 内容哈希双重校验）"。

### 反例：不分点、过于笼统

> ~~分层上下文架构：构建了三层架构，做了压缩和卸载，避免了上下文污染~~

**为什么不好**：没有分点展开，丢失了架构设计和技术决策。读者看不出具体怎么做的、为什么这么做。应拆为 3-4 个要点，每个要点聚焦一个技术决策。

## Reference 模板

详细的项目简历模板和填充指南见 `references/resume-template.md`。使用该模板时：

1. 先完成项目探查，收集事实
2. 按模板结构逐节填充，每条信息都需有代码/文档来源
3. 标注 `[待补充]` 的地方表示代码中无数据，需用户提供真实数据
4. 生成初稿后进入用户校准环节
