## 1. 设计理念：极致轻量

nanobot 的核心设计哲学是**"做减法"**——在保持完整AI助手功能的前提下，将代码量压缩到极致。

### 1.1 轻量数据

| 指标 | nanobot | OpenClaw | 对比 |
|------|---------|----------|------|
| 核心代码行数 | **4,279 行** | ~200,000+ 行 | **减少 99%** |
| Python文件数 | 59 个 | - | 高度聚焦 |
| 启动时间 | < 1 秒 | 数秒 | 秒级启动 |
| 内存占用 | < 100 MB | 数百MB | 轻量级 |

### 1.2 轻量策略

```
┌─────────────────────────────────────────────────────────────┐
│                    nanobot 简化策略                          │
├─────────────────────────────────────────────────────────────┤
│  1. 单一运行时      → 纯 Python，无 Node.js 依赖             │
│  2. 统一LLM接口     → LiteLLM 替代自研 Provider 层           │
│  3. 简化存储        → CSV/JSON 替代 SQLite+向量数据库         │
│  4. 聚焦核心        → 去除 Native Apps，专注 Server 端        │
│  5. 声明式配置      → JSON 配置 复杂 Plugin SDK              │
│  6. 技能即文件      → Markdown + Shell 替代复杂 Skill API    │
└─────────────────────────────────────────────────────────────┘
```

## 4. 关键技术决策

### 4.1 决策矩阵

| 决策点 | 选择 | 备选方案 | 理由 |
|--------|------|----------|------|
| **LLM接口** | LiteLLM | 自研/llama-index | 统一100+模型，减少维护 |
| **CLI框架** | Typer | Click/Argparse | 类型安全，自动生成帮助 |
| **配置验证** | Pydantic v2 | dataclasses/jsonschema | 强大的验证+序列化 |
| **HTTP客户端** | httpx | requests/aiohttp | 异步支持+现代API |
| **技能格式** | Markdown+Shell | JSON/Python API | 易读易写，无需编程 |
| **内存存储** | CSV/JSON | SQLite/向量DB | 简单透明，易于调试 |
| **消息总线** | 简易EventBus | Redis/RabbitMQ | 单机足够，零依赖 |

### 4.2 架构取舍

```
┌─────────────────────────────────────────────────────────────────┐
│                      nanobot 架构取舍                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │

│  3️⃣ 添加技能 (Markdown文件)                                      │
│  ┌─────────────────────────────────────────────────────────┐   │

### 5.2 与 OpenClaw 的扩展性对比

| 扩展类型 | nanobot | OpenClaw | 对比 |
|----------|---------|----------|------|
| 添加 Provider | 2步, ~5行 | 需要理解 Provider SDK | nanobot更简单 |
| 添加 Channel | ~100行 | 实现 ChannelPlugin 接口 | 两者类似 |
| 添加 Skill | Markdown文件 | TypeScript/JavaScript | nanobot更易写 |
| 添加 Tool | Python函数 | TypeScript函数 | 取决于语言偏好 |
| 自定义行为 | JSON配置 | AGENTS.md/SOUL.md | OpenClaw更灵活 |

## 7. 安全架构

### 7.1 安全层

```
┌─────────────────────────────────────────────────────────────────┐
│                      安全架构                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Layer 1: 访问控制 (Access Control)                              │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  channels.*.allowFrom: ["user_id"]                      │   │
│  │  - 空列表 = 拒绝所有 (默认)                              │   │
│  │  - ["*"] = 允许所有                                      │   │
│  │  - ["id1", "id2"] = 白名单                              │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  Layer 2: 工作区隔离 (Workspace Isolation)                       │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  tools.restrictToWorkspace: true                        │   │
│  │  - 所有文件操作限制在工作区目录                           │   │
│  │  - 防止路径遍历攻击                                       │   │
│  │  - Shell 命令受限于用户权限                               │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  Layer 3: 工具权限 (Tool Permissions)                            │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  - 工具注册时验证输入模式                                 │   │
│  │  - 敏感操作需用户确认                                     │   │
│  │  - MCP 工具超时控制                                       │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  Layer 4: 会话隔离 (Session Isolation)                           │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  - 每个用户独立会话上下文                                 │   │
│  │  - 会话历史隔离存储                                       │   │
│  │  - 记忆按用户分离                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 8. 性能特征

### 8.1 基准测试

| 场景 | 指标 | 数值 |
|------|------|------|
| 冷启动 | 启动时间 | < 1 秒 |
| 内存占用 | 空闲状态 | ~50 MB |
| 消息处理 | 端到端延迟 | 1-3 秒 (取决于LLM) |
| 并发 | 同时会话 | 无硬性限制 |
| 存储 | 记忆文件 | 每用户 ~10-100 KB |

### 8.2 优化策略

```

## 10. 总结

nanobot 通过**战略性简化**实现了极致轻量：

1. **技术栈精简**: LiteLLM统一LLM接口，Typer简化CLI，Pydantic处理配置
2. **存储简化**: CSV/JSON代替数据库，透明可调试
3. **架构扁平**: 单体架构代替微服务，减少网络开销
4. **技能简化**: Markdown+Shell代替编程API，降低门槛
5. **功能聚焦**: Server-only，放弃Native App复杂度

这种设计使nanobot成为：
- **研究原型**的理想选择（代码可读、易于修改）
- **快速部署**的首选（pip install即可运行）
- **资源受限环境**的解决方案（低内存CPU占用）

> **"做减法，直到不能再减——然后你就得到了精华。"**
