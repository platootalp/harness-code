## 一、AI Coding Agent 项目

### 1.1 架构决策（基础版）

**Q1: 你提到"Orchestrator-Worker 状态中枢"，但 AutoGPT、CrewAI 都用类似架构。你的核心差异化是什么？对比过竞品吗？**

参考回答：
- Orchestrator 是**会话级别的主 agent**，负责整体编排和决策
- Worker 是 **subagent，用完即销毁**，强调资源隔离
- 差异化体现在：
  1. **复杂度-风险双维路由机制**：不是纯启发式决策，而是通过量化指标选择处理模式
  2. **5 类专家 Agent 协作体系**：有锁机制和冲突检测，比 CrewAI 的简单协作更可控
  3. **分层上下文架构**：JIT + RAG + Memory 三级缓存，避免上下文膨胀
- 对比竞品：
  - vs AutoGPT：AutoGPT 偏重单 Agent 自主探索，我们强调结构化分解和专家协作
  - vs CrewAI：CrewAI 的 Agent 协作较松散，我们有文件锁和哈希锚定冲突检测
  - vs LangGraph：LangGraph 是图编排框架偏通用，我们的路由和 Agent 体系是面向研发场景深度定制的

> **面试重点**：如果没深入对比过竞品，可以诚实说"做过调研但没有生产环境对比"，然后强调自己的**设计取舍**而非硬撑。

**Q2: ReAct 循环的退出条件，"最大轮次耗尽"设置了多少？如果 LLM 第 8 轮突然开始幻觉但还没触发退出，怎么应对？**

参考回答：
- 最大轮次设置为 **50 轮**（依据：内部 benchmark 测试，95% 的有效任务在 40 轮内完成）
- **幻觉应对策略**：
  1. **一致性交叉校验**：用小模型对关键推理步骤做 cross-check
  2. **置信度检测**：解析 ReAct 输出，检测高置信度幻觉特征（引用不存在的文件路径/函数名）
  3. **外部验证**：对关键结论调用外部工具验证（如代码执行、文件存在性检查）
  4. **动态截断**：监控每轮输出 token 分布，发现异常模式提前终止
  5. **兜底机制**：超时强制进入人工确认环节

> **面试重点**：50 轮这个数字需要解释依据；幻觉兜底策略体现工程化思维，**建议坦诚说这块正在优化**。

**Q3: "复杂度-风险双维路由"中，复杂度 0.6 是怎么量化的？"重构 user service"为什么是 0.6 而不是 0.5 或 0.7？**

参考回答：
- **复杂度维度**（加权平均）：
  - `token_length`：代码长度（/10000 归一化）
  - `subtask_count`：子任务数（/20 归一化）
  - `cross_domain`：跨域程度（涉及技术栈数/5）
  - `io_ratio`：IO 密集度（0-1）
  - `complexity = (token_length/10k + subtask_count/20 + cross_domain/5 + io_ratio) / 4`
- **风险维度**：
  - 操作可逆性（1-5 分）
  - 影响范围（1-5 分）
  - 数据敏感性（1-5 分）
- **"重构 user service"=0.6 示例**：假设 token_length=2000(0.2) + subtask_count=8(0.4) + cross_domain=3(0.6) + io_ratio=0.8(0.8)，加权平均 ≈ 0.5-0.6
- **临界值设计**：QUICK(<0.3) / DEEP(0.3-0.7) / STRATEGIC(≥0.7)；实际选模式还要**综合风险维度**

> **面试重点**：强调权重是**人工设定+经验调优**，不是 ML 学出来的；归一化用 min-max；边界值解释要有依据。

---

**Q4: QUICK/DEEP/STRATEGIC 三种模式，切换触发条件是什么？有没有出现过模式选错导致的问题？**

参考回答：
- **触发条件**：
  - QUICK：复杂度 < 0.3 且风险 < 0.3（简单查询、格式化、小修复）
  - DEEP：0.3 ≤ 复杂度 < 0.7 或 0.3 ≤ 风险 < 0.7（常规开发任务）
  - STRATEGIC：复杂度 ≥ 0.7 或 风险 ≥ 0.7（架构重构、迁移、高风险操作）
- **模式选错案例**：
  - 简单任务走 DEEP：浪费资源，但影响可控
  - 复杂任务走 QUICK：结果不对，曾出现过，后来加了**二次确认**机制
- **自动纠正**：执行前 LLM 会输出执行计划，用户可干预调整模式

> **面试重点**：体现你有**闭环思维**，知道模式可能选错，有兜底。

---

**Q5: "5 类领域专家 Agent"协同，Reviewer 和 Coder 同时改一个文件，谁优先级高？有没有出现过 reviewer 否决但 coder 继续基于旧代码开发的情况？**

参考回答：
- **锁机制保证互斥**：文件级锁，先申请先得，其他 Agent 等待
- **Reviewer 否决处理**：
  1. Coder 收到 Reviewer 反馈后，状态更新，锁重新分配
  2. 不会基于旧代码继续开发，因为有**版本锚定机制**（LINE#ID + 内容哈希）
  3. 如果 Coder 正在执行中被否决，会触发**中断+状态回滚**

> **面试重点**：体现你对**并发协作安全**的思考，有完整的锁和状态管理。

### 1.1 架构决策（深入追问版）

#### Orchestrator 形态追问

**Q1.1: Orchestrator 是一个进程还是一个服务？如果是进程，和 Worker 之间怎么通信？**

参考回答：
- Orchestrator 是**独立进程**，每个会话一个实例
- 与 Worker 通信：**进程间通信（IPC）**，使用 Unix Domain Socket 或命名管道
- 选择理由：比 RPC 轻量，比消息队列简单，适合低延迟场景

**Q1.2: Orchestrator 的状态存在哪？进程重启后状态怎么恢复？**

参考回答：
- **内存为主**，关键状态**异步持久化到 Redis**
- 重启恢复：从 Redis 加载最近会话状态 + 从 Worker 获取正在执行任务的 checkpoint
- Redis 挂了：降级为纯内存模式，任务不丢失但无法热恢复

**Q1.3: Orchestrator 是单实例还是多实例？多实例会不会脑裂？**

参考回答：
- **多实例部署**，通过 Redis 实现**分布式锁**保证同一会话只在一个实例处理
- 脑裂防护：会话锁 + 状态同步 + 主动 health check
- 状态同步：每个实例处理的事件通过事件日志同步到其他实例

**Q1.4: 你的架构和 AutoGPT/CrewAI/LangGraph 到底有什么区别？**

参考回答：
| 维度 | 我们 | AutoGPT | CrewAI | LangGraph |
|------|------|---------|--------|-----------|
| 编排方式 | 路由+专家Agent | 单Agent自主探索 | 多Agent松散协作 | 图编排通用框架 |
| 冲突处理 | 文件锁+哈希锚定 | 无 | 无 | 无 |
| 上下文 | 分层三级缓存 | 单一 | 单一 | 可自定义 |
| 场景 | 研发任务 | 通用探索 | 业务流程 | 通用 |

**Q1.5: Orchestrator 调用 LLM 的频率是多少？**

参考回答：
- **关键节点才调**：任务分解、模式选择、子任务分配、异常处理
- 不每轮子任务都调，减少 token 消耗
- 估算：每会话 5-20 次 LLM 调用

**Q1.6: Orchestrator 自己的状态机是什么？**

参考回答：
```
IDLE → RECEIVED(收到请求) → DECOMPOSING(分解任务) → SCHEDULING(规划执行)
→ EXECUTING(执行中) → COMPLETED/FAILED(终止)
```
- 状态流转由事件驱动（收到请求、分解完成、子任务完成、超时等）

#### ReAct 循环追问

**Q2.1: 你的 Thought 是什么？是 LLM 的 reasoning 输出还是结构化的思考链？**

参考回答：
- **结构化的思考链**，包含：
  - `thought`: 当前推理
  - `action`: 要执行的工具/操作
  - `action_input`: 工具参数
  - `observation`: 执行结果
- 做过 thinking 展示，但可配置开关

**Q2.2: 你的 Action 是什么？**

参考回答：
- **工具调用**：文件读写、代码执行、搜索、Shell 命令
- **Agent 调用**：委派给专家 Agent
- **复杂操作**：生成代码并写入文件（作为原子操作）

**Q2.3: 你的 Observation 是什么？工具执行超时/错误怎么处理？**

参考回答：
- 正常：`{"status": "success", "result": "..."}`
- 超时：`{"status": "timeout", "message": "执行超时"}` → 计入重试计数
- 错误：`{"status": "error", "error": "具体的错误信息"}` → 根据错误类型决定重试或放弃

**Q2.4: "任务完成"怎么定义？**

参考回答：
- **多层验证**：
  1. LLM 自我判断"任务完成"
  2. 外部验证（执行代码、运行测试）
  3. 结果符合预期输出的比例阈值
  4. 用户确认（STRATEGIC 模式）

**Q2.5: 最大轮次为什么设 50？**

参考回答：
- 内部 benchmark：95% 有效任务在 40 轮内完成
- 预留 buffer 到 50，避免频繁截断
- 后续可根据实际数据动态调整

**Q2.6: "明确放弃"的触发条件是什么？**

参考回答：
- LLM 明确输出"做不到"或"无法完成"
- 连续 3 轮返回相似结果（疑似循环）
- 重试 N 次（N=3）仍失败
- 资源消耗超阈值

**Q2.7: 有没有做过 Thought 的一致性校验？**

参考回答：
- 用**更小的模型**对关键推理步骤做 cross-check
- 检测逻辑矛盾：前置条件和结论是否一致
- **还没有在生产环境大规模使用**，是优化方向

**Q2.8: Agent 的 Thought 是存状态里还是每次重新生成？**

参考回答：
- **存状态**，只存最后 N 轮（N=10），避免上下文膨胀
- 占 token 估算：每轮约 500-2000 tokens

**Q2.9: 遇到过最离谱的 ReAct 幻觉是什么？**

参考回答：
- LLM **编造文件路径**，说"/src/utils/helper.js 第 50 行有 bug"，实际文件不存在
- **兜底**：执行前校验文件存在性

#### 复杂度-风险路由追问

**Q3.1: 权重是人工设定还是 ML 学出来的？**

参考回答：**人工设定 + 经验调优**，不是 ML。

**Q3.2: 0.6 怎么归一化的？总分超过 1 怎么办？**

参考回答：
- **min-max 归一化**
- 每个维度先除以最大值归一化到 [0,1]
- 总分超 1：**截断到 1**，说明任务极复杂，直接进 STRATEGIC 模式

**Q3.3: 谁来计算复杂度？边执行边调整？**

参考回答：
- Orchestrator 在**收到任务时计算**，用于初始模式选择
- 执行中**不动态调整**（避免状态混乱）
- 但子任务失败会影响整体风险评估，影响后续子任务分配

**Q3.4: 风险维度怎么打分？删除/修改/配置分别打多少？**

参考回答：
- 操作可逆性：删除=5（最难），修改=3，配置=2
- 影响范围：全局=5，模块=3，局部=1
- 数据敏感性：用户数据=5，业务配置=3，代码=1
- **加权平均**得到风险分

**Q3.5: OAuth2 迁移风险 0.7，但算出来 1.0 怎么办？**

参考回答：
- **加权公式**：`risk = 0.4*可逆性 + 0.3*影响范围 + 0.3*数据敏感性`
- 超 1.0 直接截断，**强制进入 STRATEGIC + 人工审批**

**Q3.6: 风险评估时机？动态评估引入延迟吗？**

参考回答：
- 任务开始前评估一次，每个**子任务执行前动态评估**
- 延迟影响很小（<10ms），因为是本地计算，不涉及 LLM 调用

**Q3.7: 复杂度 0.2 但风险 0.9 算什么模式？**

参考回答：
- **取较高者**，走 STRATEGIC 模式
- 理由：风险高于一切，宁可慢不要错

**Q3.8: 响应延迟降低 70% 怎么算的？**

参考回答：
- **基线**：串行执行模式（一个任务从头到尾单线程）
- **测量**：同类型任务，对比串行 vs 我们的并行执行
- 吞吐量提升 2.5x 是相对串行，**并行度=子任务数/CPU 核心数**

**Q3.9: 有没有出现过模式选错？能自动纠正吗？**

参考回答：
- 有过复杂任务走 QUICK 导致结果不对
- **二次确认机制**：DEEP/STRATEGIC 模式输出执行计划，用户可干预
- 未来方向：基于执行反馈动态调整

#### 5类 Agent 协作追问

**Q4.1: 每个 Agent 的 Prompt 具体是什么？**

参考回答：
- **Planner**：分解任务，输出 DAG，有模板 Prompt + 任务上下文
- **Coder**：生成代码，包含语言框架约束、安全规则
- **Reviewer**：代码审查，包含规范检查、潜在 bug 检测
- **Tester**：生成测试用例，关联 Coder 输出
- **Executor**：执行命令，收集结果

**Q4.2: Agent 之间的通信机制是什么？**

参考回答：
- **通过 Orchestrator 中转**，不直接通信
- 共享状态在 Orchestrator，Agent 只读写自己负责的部分
- 消息传递使用结构化对象（TaskResult、ReviewComment 等）

**Q4.3: 每个 Agent 是独立进程还是同一进程的不同实例？**

参考回答：
- **同一进程的不同线程**（GIL 通过 asyncio规避）
- 状态隔离：每个 Agent 有独立的 context window
- 创建/销毁开销：<100ms

**Q4.4: 锁的粒度是什么？文件级锁效率低？**

参考回答：
- **文件级锁**，简化实现
- 确实存在效率问题，但通过**锁粒度优化**解决：
  - 锁住的是文件路径 + 行号范围
  - 不同函数（不同行范围）可以并发
- 未来优化方向：更细粒度锁

**Q4.5: Agent B 等锁期间干什么？锁超时多久？**

参考回答：
- B 进入**等待队列**，定期轮询锁状态（间隔 1s）
- 锁超时：**30 秒**，超时后任务降级或重新分配
- A 拿锁后宕机：超时自动释放锁

**Q4.6: Reviewer 否决但 Coder 基于旧代码修改，怎么处理？**

参考回答：
- **版本锚定**：每次 Review 产生新版本快照
- Coder 必须基于最新快照修改，Orchestrator 校验
- 冲突检测：哈希比对，发现不一致则中断

**Q4.7: 任务分配策略是什么？怎么避免 LLM 偏见？**

参考回答：
- **规则引擎为主**（涉及代码→Coder，涉及测试→Tester）
- LLM 建议作为参考，不直接决策
- 偏见防护：多级分配、热点检测

**Q4.8: Coder 忙，新任务怎么办？最大并发多少？**

参考回答：
- **排队等待**，队列长度 10
- 或分配给其他 Coder 实例（多实例）
- 最大并发：CPU 核心数 * 2（IO 密集型任务）

#### DAG 任务分解追问

**Q5.1: 任务必须串行吗？分析需求和写代码能不能并行？**

参考回答：
- **不一定串行**，可并行的任务会并行调度
- 如果 LLM 说反向依赖，说明**分解有问题**，触发重新分解
- 依赖关系由拓扑排序分析得出

**Q5.2: DAG 是 LLM 直接生成还是后处理？**

参考回答：
- **LLM 生成 + 后处理校验**
- LLM 输出任务列表和依赖，后处理检测环、补充隐式依赖

**Q5.3: 四维度校验不通过率？重分解成功率？**

参考回答：
- 不通过率约 **20-30%**
- 重分解成功率约 **70%**
- 3 次失败后**人工介入**

**Q5.4: 拓扑排序用 Kahn 还是 DFS？最深链多长？**

参考回答：
- **Kahn 算法**（贪心，更容易并行优化）
- 最深链长度取决于任务分解质量，通常 < 20
- 栈深度不是问题（Kahn 用队列不用栈）

**Q5.5: Kahn 输出 A D B E C F，但最优可能是 D A E B C F，怎么做最优调度？**

参考回答：
- **只保证正确性**，不保证最优调度
- 调度优化是未来方向（如关键路径优先）

**Q5.6: 检测到环形依赖怎么办？**

参考回答：
- 触发**重新分解**，prompt 强调"避免循环依赖"
- 3 次失败后**人工介入**

**Q5.7: 100 个子任务，最多并行多少？**

参考回答：
- 受 **LLM API 限流**和 **Agent 实例数**限制
- 实际并行度约 10-20

**Q5.8: Task A/B 各需 8GB，系统 10GB，会同时调度吗？**

参考回答：
- **调度器会检查资源**，不会同时调度
- 资源不足时**排队等待**

#### 分层上下文追问

**Q6.1: JIT 层 128K 是单次上限还是累计？超过怎么办？**

参考回答：
- 是**单次请求上限**
- 累计超 128K：**压缩后存入 RAG 层**，JIT 只保留最近对话

**Q6.2: RAG 检索触发条件？**

参考回答：
- **JIT 满了自动触发**
- LLM 可主动查询 RAG（通过工具调用）

**Q6.3: RAG 存储的是原始消息还是摘要？**

参考回答：
- **摘要为主**，原始消息可选保留
- 摘要级别：**每天或每 50 轮对话**生成一次摘要
- 摘要方式：**LLM 生成**

**Q6.4: 重要性评分模型是什么？**

参考回答：
- **LLM 评分**，在压缩时调用
- 评分时间点：压缩前

**Q6.5: 压缩算法是什么？**

参考回答：
- **Summarization**（LLM 生成摘要）为主
- 冗余推理链用 **LCEL**（删除重复推理步骤）

**Q6.6: 做过压缩后信息丢失率测试吗？**

参考回答：
- **做过**，语义相似度约 85-90%
- 任务完成率下降约 5%

**Q6.7: 工具结果持久化本地文件，TTL 多久？**

参考回答：
