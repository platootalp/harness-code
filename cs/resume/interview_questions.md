## 题目一：任务分解质量保证

### 题目

**如何保证任务分解的质量？如何确定任务分解是有效的？通过什么方式评测？**

---

### 参考答案

#### 一、任务分解质量的四个核心维度

根据 Mozi 项目的 Task 模块设计（见 `docs/init/module/2026-03-29_task.md`），任务分解质量通过以下四个维度评估：

| 维度 | 判断标准 | 实现方式 |
|------|----------|----------|
| **完整性** | 所有子任务覆盖原目标，无遗漏 | 集合覆盖检查：child tasks' goals ⊇ original goal |
| **原子性** | 子任务不可再分，粒度合适 | 粒度阈值：执行时间 < N分钟，或单一工具调用 |
| **独立性** | 无隐式依赖，可独立执行 | 共享资源检测：文件、环境变量、状态 |
| **可验证性** | 有明确的完成标准 | 每个 task 有 expected_output 描述 |

#### 二、质量保证策略

Mozi 采用 **LLM 驱动 + 规则约束的混合策略**：

```
TaskDecomposer
    │
    ├──► LLM 生成候选子任务（理解任务意图）
    │
    ├──► 规则验证层检查（分解完整性和可执行性）
    │
    └──► 优化层（合并过细粒度任务）
             │
             ▼
      DecompositionValidator 验证有效性
```

#### 三、评测方式

1. **DecompositionValidator 自动验证**
   - 完整性：LLM 判断子任务是否覆盖原始目标所有方面
   - 原子性：检查子任务步骤数 ≤ MAX_STEPS_PER_TASK (5)
   - 独立性：`_detect_shared_resources()` 检测共享资源冲突
   - 可验证性：检查每个子任务是否有 `expected_output`

2. **验证失败处理流程**
   - 完整性失败 → 重新分解，增强约束
   - 原子性失败 → 合并或拆分粒度
   - 独立性失败 → 调整执行顺序或合并任务

3. **实际效果评估**
   - **A/B 测试**：对同一任务使用不同分解策略，对比分解结果的质量指标（完整性、原子性等维度得分）
   - **在线实验**：线上部署不同版本分解器，对比子任务成功率、执行效率、失败率等核心指标
   - **人工评估**：抽样让人类专家评审分解质量，作为 ground truth 校准自动评估器

### 追问设计

#### 追问 1：粒度控制

**问题**：如果任务分解过细（如每项 <2h），会带来什么管理成本？如何平衡？

**参考要点**：
- 管理成本：任务切换开销、上下文切换损耗、状态管理复杂性增加
- 过细的粒度：增加调度开销，降低并行效率
- 过粗的粒度：难以跟踪进度，无法有效容错
- 建议范围：0.5d～3d 为宜

#### 追问 2：隐式依赖处理

**问题**：遇到跨团队依赖时，如何处理任务分解中的灰色地带？

**参考要点**：
- 显式依赖：通过 `blocked_by` / `dependents` 字段明确管理
- 隐式依赖（共享文件、环境变量、状态）：通过 `_detect_shared_resources()` 检测
- 跨团队灰色地带：
  - 通过接口契约明确边界
  - 增加虚拟依赖任务作为同步点
  - 使用 DAG 图结构维护完整依赖链

#### 追问 3：LLM 分解质量波动

**问题**：LLM 分解任务的质量和一致性难以保证，你的解决方案是什么？

**参考要点**：
- LLM 分解的问题：粒度不一致、遗漏依赖、缺少验收标准
- 混合策略：LLM 生成 + 规则验证 + 人工复核
- 规则约束：
  - MAX_STEPS_PER_TASK 限制原子性
  - expected_output 要求可验证性
  - 共享资源检测保证独立性
- 多次生成 + 验证器筛选

#### 追问 4：实战经验

**问题**：举一个你经历过的任务分解失败的案例，原因是什么？你是如何改进的？

**参考要点**：
- 典型失败场景：
  - 遗漏边界条件导致返工
  - 依赖关系分析不足导致死锁
  - 粒度把握不当影响进度可视化
- 改进措施：
  - 增加 DoD (Definition of Done) 检查
  - 引入同行评审机制
  - 建立分解检查清单

#### 追问 5：部分成功场景

**问题**：如果任务分解后部分子任务失败，如何处理？什么情况下可以接受部分成功？

**参考要点**：
- Task 模块设计：TaskResult 支持 `child_results` 列表记录每个子任务结果
- ResultAggregator 整合结果时保留失败信息
- 可接受部分成功的场景：
  - 非核心路径的辅助任务失败
  - 用户明确授权降级处理
  - 失败项可独立修复，不阻塞主流程
- 不可接受的场景：核心功能路径失败、数据一致性受损

### 评分标准

| 等级 | 标准 |
|------|------|
| **优秀** | 能完整阐述四维度质量模型，理解 LLM+规则混合策略，有实战案例 |
| **良好** | 知道四维度含义，能说明基本的验证方法 |
| **及格** | 理解分解质量重要性，能说出一两种验证方式 |
| **不及格** | 缺乏分解质量意识，认为分解只是"拆分任务" |
